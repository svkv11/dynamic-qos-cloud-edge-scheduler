## 2. Problem statement and objectives

Heterogeneous workloads have different CPU, memory, GPU, latency, priority, and deadline requirements. A scheduling policy that considers only task order or resource availability may not adequately represent these differing requirements.

The project develops and evaluates a Dynamic QoS-aware cloud-edge task scheduling approach. It compares conventional baseline policies, the proposed deterministic Dynamic QoS policy, and a Deep Q-Network (DQN) policy.

### Main objectives

1. Model heterogeneous workloads and configured cloud-edge resources.
2. Represent task requirements in a structured form.
3. Interpret natural-language workload requirements using a GenAI component.
4. Schedule tasks based on resource suitability and QoS-related requirements.
5. Compare Round Robin, Resource Only, Dynamic QoS, and DQN.
6. Evaluate simulated execution time, deadline success, QoS, and resource-related behavior.
7. Analyze policy differences statistically.
8. Document limitations and avoid unsupported performance claims.

## 4. Scheduling policies

The project evaluates four policies.

### 4.1 Round Robin

A baseline scheduling strategy that distributes tasks using a rotating node-selection order.

### 4.2 Resource Only

A baseline policy that focuses on resource suitability when selecting a node.

### 4.3 Dynamic QoS

The proposed deterministic scheduling policy considers resource suitability, task priority, and node-aware deadline requirements.

The configured weights are:
- Resource suitability: 0.80
- Priority: 0.10
- Node-aware deadline: 0.10

The implementation also includes modes:
- `full`
- `no_priority`
- `no_deadline`

These modes support investigation of the contribution of priority and deadline awareness.

### 4.4 DQN

A Deep Q-Network scheduling policy that selects among the three simulator nodes.

Action mapping:
- Action 0: `edge-01`
- Action 1: `edge-02`
- Action 2: `cloud-01`

The DQN policy is evaluated separately from the deterministic scheduling policies and must be interpreted using the actual experimental configuration.

### 9.2 Potential action-mask inconsistency

The action-selection implementation masks infeasible actions.

However, the target computation in `ml/dqn_agent.py` uses:

`next_q_values = self.target_net(next_states).max(dim=1).values`

The replay buffer stores:

`(state, action, reward, next_state, done)`

It does not store the next-state action mask.

Therefore, action selection and target-value computation may use different feasibility assumptions.

This is a verified implementation observation. Its impact on the final DQN policy has not been established. Do not modify it until the investigation supports a change and the user approves it.
